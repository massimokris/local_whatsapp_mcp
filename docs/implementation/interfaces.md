# Component interfaces

These are the integration contracts between the native app, local service, and pinned engine.

## Layout and binaries

- `backend/`: Go module `github.com/massi/localwhatsappmcp`; main `cmd/localwhatsappmcp` builds `localwhatsappmcp` (service and private app control).
- `native/`: Swift package producing executable `LocalWhatsAppMCP`.
- `vendor/wacli/`: upstream pin metadata, focused patch, and build integration; downloaded checkout is build output, not source-controlled wholesale.
- App bundle: `Contents/MacOS/LocalWhatsAppMCP`, `Contents/Helpers/localwhatsappmcp`, `Contents/Helpers/wacli`.
- Default runtime directory: `~/Library/Application Support/LocalWhatsAppMCP/` (0700). App control uses `control.sock` (0600), separate from the loopback MCP listener.

## Service/private control boundary

Native app launches `localwhatsappmcp serve --owner-stdin --data-dir DIR --wacli PATH`. The app keeps stdin open as an ownership pipe; EOF cancels the service and awaits owned children, including after an app crash. SIGTERM also waits for owned child shutdown. Service stderr emits only a bounded, allowlisted `startup_error` code for startup failure; native UI maps it to recovery copy. It never displays arbitrary process logs. Private app calls use `localwhatsappmcp control --data-dir DIR --method METHOD --path PATH`; JSON request body comes from stdin; one JSON response goes to stdout; nonzero status indicates failure. Blocking process work stays off the main actor.

The service takes an exclusive `service.lock` in its data directory. Before publishing policy after a crash, startup also waits for the upstream writer lock; a stale lock file alone does not prove a writer is running. Only wacli writes its message/session databases; the service's direct SQL reads supply catalog metadata and persisted sync freshness.

Private endpoints:

| Method/path | Request | Response |
| --- | --- | --- |
| `GET /state` | none | state described below |
| `POST /whatsapp/connect` | `{}` | state |
| `POST /whatsapp/disconnect` | `{}` | state after linked-device logout; retryable error on failure |
| `POST /lifecycle/wake` | `{}` | state |
| `GET /catalog` | none | `{"chats":[...]}` complete minimal local catalog |
| `PUT /scope` | `{"mode":"all" or "selected","chat_ids":[...]}` | state after policy transition |
| `POST /pairing` | `{"name":"Connection 1"}` | `{"invitation_id":"...","instructions":"...","expires_at":"RFC3339"}` |
| `POST /agents/manual` | `{"name":"Connection 1"}` | `{"id":"...","name":"Connection 1","url":"http://127.0.0.1:32191/mcp","access_token":"..."}` |
| `GET /agents/ID/credentials` | none | same connection details, for any active grant with a stored credential |
| `PATCH /agents/ID` | `{"send_enabled":true}` | state |
| `DELETE /agents/ID` | none | state |

State is JSON with `whatsapp` (`status`, `detail`, `linked`, `sync_state`, optional `disconnect_pending`, `qr`, `last_event_at`, `last_synced_at`), `scope` (`mode`: `initial`, `all`, `selected`; `chat_ids`; `revision`), `agents` (array of `id`, `name`, `client`, `send_enabled`, `connected`, optional `last_seen_at` and `pairing_invitation_id`), `mcp` (`url`, `status`), and optional `error`. Chat rows contain `id`, verified `aliases` (optional array including the current and previous identities), `name`, `phone`, `kind` (`direct`/`group`), `archived` (boolean), `last_activity` RFC3339. Errors use `{"error":"readable safe message"}`. Native decoder should tolerate missing optional fields.

`archived` reads wacli's existing `chats.archived` SQLite column through the read-only catalog query and is included for both true and false values in private `/catalog` and scoped MCP `find_conversations` results. wacli owns archive/unarchive synchronization and schema migration. The field represents the last stored WhatsApp state, which can lag phone changes before app-state replay completes or while offline. It neither changes selected scope nor authorizes a write to WhatsApp.

The optional `invitation_id` in a pairing response is a non-secret correlation identifier, persisted with that invitation. Redemption copies it to the saved grant as `pairing_invitation_id`; `/state` exposes it so the native UI can recognize its exact redeemed invitation and clear temporary instructions. Do not infer redemption from an agent’s display name or client type: separate invitations may use identical values. Older invitations/grants may omit these additive fields. The identifier does not authenticate an agent or replace the single-use pairing token.

The native app chooses the first unused `Connection N` name for new connections and sends it in these requests; the setup screen has no name field or client selector. Existing names remain unchanged. The optional legacy `client` field on invitation creation remains accepted and ignored. New invitations use the generic connection flow regardless of that value. The service produces instructions containing the actual loopback exchange URL, temporary code, JSON POST format, expiry, and the agent's responsibility to save credentials, configure its own MCP client, and verify `check_status`. Copied instructions use five paragraphs: connection, exchange, credential handling, verification/expiry, and the final capabilities brief with one or two example requests. Keep two blank lines after the connection and exchange paragraphs, one blank line between the remaining paragraphs, and the JSON body inline with the exchange instructions. The verification/expiry paragraph retains the notice that sending starts disabled. The native Copy instructions action creates and copies that text in one step.

Connection icons are native presentation only. Every connection uses the `apple.terminal` SF Symbol, falling back to `terminal` when the preferred symbol is unavailable on older macOS. The service does not select, persist, or return icon metadata. Ignore legacy `icon` fields in saved JSON and service responses; existing names, grants, and credentials remain unchanged. Creation requests and the HTTP pairing exchange response are unchanged.

Manual creation requires confirmed scope, persists an ordinary grant with `client: "manual"` and sending disabled, and returns its full MCP URL plus durable bearer credential. `GET /agents/ID/credentials` supports all active grants with a stored credential, including generic paired connections. Retrieval reuses the existing token without creating or rotating a grant or changing sending permission. Revoked, missing, or unavailable stored credentials fail instead of being regenerated. Creation and saved-credential responses use only private app control; no HTTP route, `/state`, logs, or MCP tool exposes existing connection credentials. The separate HTTP pairing exchange returns only the credential for its newly paired connection.

Manual setup uses inline URL/token rows with copy icons. Saved connections load their existing credentials automatically when expanded, showing separate URL and Token action rows with each value beneath its label and a Copy button on the right; there is no separate Credentials disclosure. Copy feedback changes the corresponding button to Copied. Display the full values, applying middle truncation only when available width requires it; the copy action always copies the complete value. Manual creation leaves setup open for copying and reuses the saved connection while that setup remains open. The native app clears transient credentials on collapse, navigation, panel close, deletion, or Quit, retaining explicitly copied URL/token values and instructions on the clipboard for pasting. Navigation clears the in-app invitation without revoking its still-valid server code. The private credential database remains the durable source. Pairing completion uses `pairing_invitation_id` to return to the overview with Local MCP expanded; an unrelated grant appearing in state is not completion of the pending invitation.

On the overview, clicking Local MCP expands URL, Token, Allow message sending, and Delete connection, in that order, for the first saved connection in name/ID order. The expanded WhatsApp card shows Choose connected chats before Stop syncing WhatsApp. The simplified home surface omits the connection list and additional-connection creation action. Existing grants remain independently stored and authorized. With no saved connections, Local MCP opens initial agent setup; completing manual setup also returns to the expanded overview card. Existing-connection credential responses may populate the home rows only while the same connection is still selected and expanded. Collapsing the card, changing the displayed connection, or leaving the page invalidates pending credential responses. The overview cards scroll to keep expanded controls and credentials reachable.

`last_synced_at` reads the pinned engine's persisted `retrieval_state.last_sync_at` marker through a bounded, read-only archive query. It records successful sync activity (including offline backlog replay), survives app restarts, and is omitted while unavailable. Transport connection, history-start, policy, QR, and heartbeat events do not advance it. `last_event_at` is event receipt time and must not be used as archive freshness. Neither timestamp proves complete WhatsApp history.

`whatsapp.sync_state` is independent of connection `status` and has four values: `unknown` (fresh completion evidence is unavailable), `syncing` (available updates are arriving or still being saved), `caught_up` (all selected-chat work through the current WhatsApp delivery boundary has been saved), and `error` (known message retrieval/persistence failure or unavailable engine health). Private `/state` and authenticated MCP `check_status` return the same WhatsApp status model. Catch-up covers available updates, not complete historical coverage.

Startup, reconnect, wake, and chat-scope changes invalidate completion. New message/history work changes catch-up to `syncing` until the corresponding processing and writes finish; a quiet healthy connection can stay `caught_up` indefinitely. Disconnect, process exit, failed connection checks, and expired engine liveness remove success. Reconnection alone cannot clear known failed work: recovery must successfully save the affected work. Expected content-policy exclusions and optional attachment downloads do not block message catch-up.

For a healthy connection the native header renders `Synced just now · 1,292 chats connected` only for `caught_up`, and `Syncing messages… · 1,292 chats connected` while completion is unknown or work is pending. It retains existing reconnect/disconnect/error copy and the count derived from saved scope. A missing or unfamiliar sync state never authorizes the success label. The native app clears cached success synchronously when wake, reconnect, or a scope change begins, and when a service-state read fails; delayed responses cannot restore the invalidated state. Timestamp age does not select either label.

Before publishing its first state for a saved sync intent, startup calls the engine's bounded `RestoreSession` operation after publishing the saved content policy. Read-only `auth status` verifies the upstream session's `authenticated` value; sync intent alone does not establish that QR linking succeeded. A verified saved session reports `linked: true` while reconnecting, so native routing skips QR setup. Intentional disconnect skips restoration. New QR or logged-out events supersede restored authentication state.

WhatsApp disconnect persists the user's intent before stopping and awaiting the sync writer, then calls the pinned engine's `auth logout`. Read-only `auth status` makes retries safe if a previous logout finished but its response was lost. This invalidates the linked-device session; it does not delete the message archive, chat scope, local agent grants, or attachment cache. A failed/interrupted logout stays in an attention state with `disconnect_pending: true`, so the UI offers Retry disconnect instead of Reconnect. The flag remains true during `disconnecting` and is omitted after successful logout. Wake, scope changes, and service restart must not reconnect; only an explicit Connect after logout completes can resume linking. Sends and remote media retrieval are blocked while intentionally disconnected. Authorized archive reads and existing attachment URLs remain available; new attachment requests use read-only `media download --cache-only`, which returns only verified cached bytes and fails offline on a cache miss. Disconnect serializes with scope changes and MCP work, cancelling pending requests before stopping the writer. The private socket is its only transport.

Native UI keeps selection/search locally, filters the complete minimal catalog, and sends the selected stable IDs. It canonicalizes each verified alias group to a current catalog row, preferring a phone-number JID when present; removing that row removes all its aliases. Display names and formatted phone strings never prove identity. Private endpoints do not require bearer credentials because the user-owned socket is the access boundary; none is mounted on the HTTP MCP listener.

## Engine policy boundary

Patched wacli accepts global `--content-policy PATH`. A required, versioned policy JSON has `version:1`, `revision:integer`, `mode:"initial"|"all"|"selected"`, `chat_ids:[stable JIDs]`. Absence/corruption when flag is supplied fails closed. It emits `policy_loaded` with revision through NDJSON lifecycle events. Supervisor stops and awaits old writer before atomic policy replacement/restart and awaits acknowledgement before access resumes. Every app-owned wacli command supplies the same fixed store and policy path. Engine ownership remains upstream.

Each supervised engine process receives a fresh `WACLI_SYNC_RUN_ID`. Explicit `sync_state` transitions and periodic `sync_snapshot` events carry `data.run_id`, a monotonically increasing `data.connection_id` within that process, `data.revision` for its immutable scope, and `data.state`. The supervisor accepts completion only from a current-run/current-revision `sync_state` event for the active connection. Older connections, old processes, and old scope revisions cannot restore success. Snapshots arrive every five seconds and maintain liveness; they can invalidate success but never independently establish catch-up. A twenty-second watchdog expires liveness and removes success when snapshots stop, including while an engine process remains alive.

The focused `whatsmeow-delivery.patch` instruments the pinned dependency's receive/handler boundary before queue admission. The offline marker does not establish completion while any earlier received handler remains queued or running, including work processed out of order. Patched wacli combines that boundary with message/history processing and asynchronous persistence completion. Its private `store/sync-debts.json` journal records outstanding work before processing; successful recovery clears only the matching work. The engine owns this journal alongside its archive, and a missing current completion event can never be reconstructed from `last_synced_at`.

App-state journal entries include their event kind, required collections and a durable sequence. A successfully persisted full snapshot clears only the earlier work it covers; later failures and unrelated work remain. Startup reconstructs missing collection-recovery markers from the journal. Older opaque event records require an exact successful action replay, ignoring only the full-sync delivery flag. Receipt entries retain identifiers, type and timestamp so startup can retry local persistence under the current scope and saved account identity without sending a receipt or message. Empty receipt message IDs are skipped while valid IDs in the same batch are still saved. Unknown legacy failures remain visible until their recovery can be verified.

An SDK undecryptable-message event is expected unavailability only when both `is_unavailable` and its explicit `view_once` type establish intentional absence. It retains a warning but creates no permanent sync debt; an exact matching event may settle an older false failure for that message only. Unknown types and hidden decryption failures remain errors. Neither the event name nor the hide flag alone proves missing recoverable content or harmless control traffic.

New unresolved decryption work records allowlisted classification flags, the original timestamp and stable sender identities in the private engine journal before handling. No message bodies, display names, cryptographic keys or arbitrary error strings are stored. The evidence survives restart without changing recovery or completion rules. Older records with no evidence remain unclassified; observation time is not their message timestamp.

The engine's opt-in `sync --repair-sync` maintenance mode requests full app-state replay for opaque legacy event failures and bounded primary-device protocol recovery for missing non-mutation messages. It preserves all archive data and unresolved failures; request acceptance does not establish recovery. The app's ordinary sync startup and MCP tool surface do not enable this mode.

A fresh baseline requires explicit operator approval to acknowledge older unverified work. With the app stopped and both service and engine writer locks held, maintenance first preserves a full private backup and durably archives the exact journal plus a scope/hash/count acknowledgement under `store/sync-baselines/`, then atomically empties only the active journal. Messages, media, session data, credentials and scope are preserved. The acknowledgement is not recovery evidence; normal restart must supply a new delivery boundary before reporting catch-up. Neither reconnect nor ordinary startup performs this reset.

## Local MCP boundary

The service binds Streamable HTTP to an explicit loopback IP address, `127.0.0.1:32191` by default; non-loopback listen addresses are rejected. Requests may target the local listener host or a valid DNS subdomain of `ngrok-free.app`, optionally on port 443. The apex domain, deceptive suffixes, malformed names and other public hosts/ports are rejected. Forwarded headers do not grant another host or select response URLs.

For a local Host, an optional Origin may be the local origin or an allowed HTTPS ngrok origin. For an ngrok Host, an optional Origin must match that host over HTTPS. Absent Origin is allowed. Host/origin rejection happens before pairing-code consumption or content access. The listener serves authenticated MCP and attachments plus the one-use pairing exchange; invitation creation and grant management stay on the user-owned Unix control socket. Both routes use the same credentials, scope, revocation and sending checks.

The user manages ngrok and supplies its URL to the remote agent. Private copied instructions, manual/saved credentials and `mcp.url` retain the local address; the user substitutes the current HTTPS tunnel base for remote setup. HTTP pairing responses and attachment URLs use the validated request base: HTTPS for an allowed ngrok Host, otherwise the local listener URL. There is no saved public URL, tunnel discovery, native tunnel setting, provider process management, or OAuth flow.

| Method/path | Request | Response |
| --- | --- | --- |
| `POST /pairing/redeem` | `Content-Type: application/json`, body `{"token":"<temporary pairing code>"}` | `{"id":"...","url":"http://127.0.0.1:32191/mcp","access_token":"...","token_type":"Bearer"}` |

The exchange authenticates possession of the random pairing code; no existing access token is required. Codes expire after ten minutes and are consumed once while creating a named connection with sending disabled. The returned URL includes `/mcp` on the validated local or ngrok request base. Send the code in the JSON body, never in the URL. The body is limited to 4096 bytes and must contain exactly one non-empty string field, `token`; duplicate keys, unknown fields, and trailing JSON fail. Credential responses are non-cacheable. The agent saves the returned token privately, configures its own client, and verifies `check_status`; the service does not know or modify client configuration. A consumed invitation is not a recovery credential: if its successful response is lost, create a new invitation and remove the unused connection as needed.

Manual UI setup still creates a grant through private control and lets the user copy its URL and bearer token directly into a Streamable HTTP client. Both paths use the same grant authentication and revocation. Every MCP request rechecks current scope, credential revocation, and sending permission. Invitation creation and redemption require confirmed scope; content remains unavailable while scope is unconfirmed.

Send tools require a caller-generated `request_id`. The service durably records an uncertain outcome before dispatch and never dispatches the same agent/request identifier again. An unchanged retry returns its saved outcome; different content with that identifier is rejected. A transport error is not proof that nothing was sent: inspect the conversation before deciding whether to send again. Accepted sends are distinct from observed delivery/read state.

Text sends use the engine’s supported self-send opt-in after the same scope and sending-permission checks. Self-send acceptance still does not guarantee delivery.

A definite pre-send rejection returns `status: "failed"` and a safe `error`; unrecognized errors, timeouts, interrupted processes and malformed responses remain `status: "uncertain"`. Send outcomes retain their safe diagnostic for unchanged retries, including after restart, without another dispatch. Only known pre-send engine errors are classified as failed; raw engine logs are never returned or saved in the send ledger. Existing uncertain records remain protected and are not retried after an upgrade.

The client-specific installer and `setup`, `headers`, `doctor`, and `stdio` commands are removed. The bundled executable retains `serve` and `control` for the native app. Existing bearer grants retain their identity and permissions; clients referencing removed commands must be reconfigured by their agent. The app does not rewrite those files. Setup uses generic copyable instructions and an inline manual option; saved connections expose credentials and permission management in expandable cards.

Legacy cloud settings must not restore provider management or OAuth access; ignore their configuration and remove hosted-agent grants while preserving local credentials and sending settings. The ngrok host allowance is built in and has no saved configuration. The current service does not start provider processes or expose their setup commands. The superseded cloud boundary is retained in the [historical implementation record](comments/104-cloud.md#superseded--2026-10-23); the [ngrok host allowance](../wayfinder/comments/001-product-contract.md#ngrok-host-allowance--2026-10-27) records the current transport exception.

## Local credential storage

`credentials.db` lives beside `settings.json` in the 0700 app data directory. The SQLite database and journals use 0600 permissions. Values are parameterized SQL data in `credentials(namespace, account, value)`; the app adds no database encryption. Cursor/attachment tokens use namespace `com.localwhatsappmcp.cursor`, account `archive`; agent bearers use `com.localwhatsappmcp.agent`, keyed by connection ID. HTTP pairing returns the new connection's bearer token to the redeeming agent. Explicit manual creation and saved-credential responses return only the selected active connection's token through private app control. Logs and general state responses remain redacted. The generic instructions contain only a temporary pairing code and ask the agent not to print its persistent access token; the service cannot control whether the agent records the exchange response.

The settings marker `credential_storage_version: 1` records completed migration. Before publishing that marker, startup creates the SQLite cursor key and rotates active grants with matching saved connection metadata, retaining their IDs and permissions. Committed SQLite values are reused if saving settings is interrupted. No Keychain reads, writes, deletion, or fallback occur in the application. Existing checkpoints expire when the old key is replaced. After migration, missing/corrupt keys or mismatched managed agent credentials yield `credentials_unavailable`; restore `credentials.db` and `settings.json` from a matching backup. WhatsApp linking and archive files are separate and unchanged.
